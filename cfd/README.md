# Офлайн-контур CFD: короткий вход

План, пороги и порядок работ — [docs/cfd-validation.md](../docs/cfd-validation.md).
Здесь только то, что нужно, чтобы запустить.

Решателя на машине разработчика нет и может не быть: тяжёлый расчёт идёт на
Linux-машине. Поэтому всё, что стоит ДО решателя и ПОСЛЕ него, работает и
проверяется без него — этим и занимается `make t-cfd`.

---

## Решатель

На этой машине стоит **нативная сборка OpenFOAM v2306 для macOS arm64**:

```sh
brew tap gerlero/openfoam
brew install --cask gerlero/openfoam/openfoam@2306
openfoam2306 -c 'echo $WM_PROJECT_VERSION'
```

Нативная, а не контейнер, по одной причине: образы OpenFOAM собраны под x86, и
на Apple Silicon они идут через эмуляцию — для CFD это разница в разы. Запуск
выбирается сам (`cfd/lib/runners.py`, `detect_runtime`): нашёлся `openfoam2306`
— нативно, нашёлся `docker` — контейнером; можно заставить через
`CFD_RUNTIME=docker`.

Требование §3.1 при этом не отменяется: `solver.image` остаётся обязательным и
остаётся с отпечатком. У нативной установки отпечаток — sha256 распространяемой
сборки, он записан в формуле Homebrew и стоит в манифестах:
`openfoam-app-arm64:2306@sha256:d7f74d…`. Смысл поля не в том, что это
непременно контейнер, а в том, что по нему восстановима та же программа.

## Команды

```sh
make cfd-validate                     # проверить манифесты случаев
make cfd-image                        # собрать образ решателя, взять digest
make cfd-geometry                     # STL в осях CFD + тела этапа 0
make cfd-case  CASE=cfd/cases/verification/naca0012-a10-medium.json
make cfd-run   CASE=... RUNNER=local  # local | ssh:host:/путь | slurm:host:/путь
make cfd-collect RUN=out/cfd/runs/naca0012-a10-medium
make cfd-slices  RUN=out/cfd/runs/naca0012-a10-medium   # поля для картинок
make cfd-convergence FAMILY=verification
make cfd-compare     FAMILY=hull-resistance
make cfd-report      FAMILY=hull-resistance             # Markdown
make cfd-html                                           # HTML с графиками
```

Очередь считает случаи **по одному**:

```sh
.venv/bin/python cfd/scripts/queue.py --dry     # план
.venv/bin/python cfd/scripts/queue.py --only keel-u200-a06-medium
```

По одному — не осторожность, а необходимость: OpenFOAM берёт столько ядер,
сколько ему велено, и два случая по четыре процесса на десяти ядрах идут не
вдвое быстрее, а втрое медленнее каждый. Один раз это уже стоило двух убитых
расчётов и load average под шестьдесят.

То же без `make` — одной точкой входа (§3.6):

```sh
.venv/bin/python cfd/cfd.py validate
.venv/bin/python cfd/cfd.py case --case naca0012-a10-medium --force
```

`--case` понимает и путь к файлу, и `case_id`.

Отдельные скрипты из §3.4 (`cfd/scripts/prepare_geometry.py` и остальные) —
обёртки над теми же командами. Код один: у `make` и у прямого вызова не должно
быть двух разных поведений.

## Как устроено

```
cfd/
  cfd.py              единая точка входа
  lib/
    axes.py           переход осей и разбор сил; три строки арифметики на виду
    manifest.py       схема 1 и строгая проверка случая
    geometry.py       STL, замкнутость, союзы тел, канонические тела этапа 0
    openfoam.py       разворачивание манифеста в каталог решателя
    forces.py         разбор истории сил, окно усреднения, статистика, логи
    convergence.py    тройка сеток, порядок, GCI, ворота §4.2
    simbridge.py      вопросы к realtime-модели
    report.py         правило статуса и Markdown
  bridge/
    sim_query.mjs     ответы даёт node теми же функциями, что считает лодка
  templates/          шаблоны OpenFOAM
  cases/              манифесты случаев
  images/             Dockerfile решателя
  golden/             принятые эталонные таблицы
  reports/            собранные отчёты
out/cfd/              всё производное; в git не идёт
```

### Шаблоны

| шаблон | решатель | для чего |
|---|---|---|
| `openfoam-aero` | `simpleFoam` | однофазный RANS: риг, изолированные крылья, тело для проверки знаков |
| `openfoam-2d` | `simpleFoam` | плоское сечение: тонкий слой с плоскостями симметрии |
| `openfoam-halfspace` | `simpleFoam` | полупространство: киль с корневой симметрией, корпус двойным телом |
| `openfoam-vof` | `interFoam` | свободная поверхность: сопротивление корпуса, боковая гидродинамика |
| `openfoam-manoeuvre` | `SRFSimpleFoam` | принудительное рыскание во вращающейся системе |

Про плоский шаблон отдельно. Первая версия ставила боковые грани `empty` и
одну ячейку поперёк, как принято в плоских случаях OpenFOAM. Так нельзя:
`snappyHexMesh` дробит ячейку во всех трёх направлениях сразу, и после первого
же уровня сгущения поперёк оказывается две ячейки, а `empty` требует ровно
одной. Сеточник при этом не падает — падает решатель, и уже на чужой машине.
Слой с симметрией даёт то же решение и не ограничивает сгущение.

Про полупространство. Один шаблон закрывает два разных вопроса, и это не
совпадение: в обоих случаях тело зеркально относительно горизонтальной
плоскости. Киль с корневой симметрией даёт удлинение вдвое против
геометрического — верхнюю границу эффекта концевой шайбы от днища, который в
симуляторе учтён множителем 1.5. Корпус двойным телом ставит ту же плоскость по
КВЛ: волнообразования нет вовсе, зато вязкая часть и сопротивление формы
считаются на ноутбуке за двадцать минут вместо суток.

Шаблон наследуется от другого файлом `_extends`. Это нужно затем, чтобы разница
между воздухом и водой читалась списком файлов, а не диффом трёхсот строк.
Языка шаблонов нет нарочно: подстановка `{{имя}}` и ничего больше. Шаблон
обязан оставаться читаемым как случай OpenFOAM, а словарь с циклами и условиями
глазами не читается — и читать его приходится каждый раз, когда расчёт ведёт
себя странно.

### Оси

Один переход, `cfd/lib/axes.py`:

```
X_cfd =  X_export        X в нос
Y_cfd = -Z_export        Y на ЛЕВЫЙ борт
Z_cfd =  Y_export        Z вверх
```

Левый борт — не выбор вкуса: он измерен в симуляторе и записан в
[docs/axes.md](../docs/axes.md) §1, и из него выведены знаки крена, руля и борта
паруса. Батарея проверяет определитель (+1, зеркала нет), три базисных вектора
и зеркало галса.

### Чистота запуска

Каталог решателя разворачивается целиком и заново, а рядом кладётся `case.json`
с отпечатком каждого написанного файла. `collect` их сверяет: правка руками
внутри развёрнутого каталога делает запуск грязным, и в `golden/` он не идёт
(§3.5). Грязное рабочее дерево git помечается там же.

### Что попадает в git

Шаблоны, манифесты, скрипты, компактные сводки и отчёты. Сетки, поля решателя
и временные каталоги — в `out/cfd/`, мимо git. Сводка обязана позволять
восстановить тяжёлый артефакт по `case_id` и отпечаткам.

## Порядок первого захода

По §8 документа:

1. `make cfd-image`, digest — в манифесты;
2. `make cfd-geometry` — проверить, что все тела замкнуты, а союз связен;
3. закрыть этап 0: `naca0012-a10-*`, `still-water`, `axes-probe` с парой
   `axes-probe-mirror`;
4. одна тройка сеток корпуса: `hull-u250-{coarse,medium,fine}`;
5. киль: `keel-u200-a6-medium` и его тройка;
6. сечение паруса — после того, как появится его выгрузка;
7. расширять матрицу только после того, как замкнётся полный контур
   «геометрия → случай → расчёт → сводка → сходимость → сравнение».

Первый milestone закрыт, когда одна команда воспроизводимо строит три сетки,
запускает случаи, собирает силы, оценивает сходимость и показывает сравнение с
симулятором.

## Что осталось

Честный список — чтобы его не пришлось выяснять по отсутствию файла.

- **Этап 0 не закрыт.** Опубликованный набор NASA Turbulence Modeling Resource
  переехал, верификационный случай OpenFOAM отдаёт 403, и сверять полученные
  Cl с Cd не с чем. Пока сверка не сделана, у всех чисел статус «посчитано», а
  не «проверено».
- **Плоский случай не сходится.** У слоя с симметрией невязка по `Uz` не падает
  вовсе, сила гуляет на семьдесят процентов от среднего, а поле показывает
  отрыв там, где на шести миллионах Рейнольдса его быть не должно. Похоже на
  паразитное поперечное течение в слое. Правильное решение — структурная C-сетка
  вместо `snappyHexMesh`, и это отдельная работа. Трёхмерные случаи этой
  болезнью не страдают: у них разброс силы — сотые доли процента.
- **Расхождение по килю не объяснено.** CFD даёт наклон кривой подъёмной силы
  вдвое-втрое меньше, чем следует из удлинения. Считается опыт на размер домена;
  второй подозреваемый — стык корня пера с плоскостью симметрии (смоченная
  площадь вышла на восемь процентов меньше геометрической).
- **Двойное тело смачивает транец.** Часть сопротивления от давления из-за
  этого завышена, а несимметричный отрыв за транцем даёт боковую силу на нулевом
  дрейфе. Вязкую часть это не портит: она легла на ITTC-57 с коэффициентом формы
  1.16.
- **Выгрузка парусов.** Формы сечений живут в `sim/membrane.js`; STL из них
  никто не пишет. До этого `sail-2d` и `rig-3d` проходят `validate`, но не
  разворачиваются.
- **Свободные heave/pitch.** Серия §5.4 со свободной посадкой требует
  `dynamicMeshDict` с шестью степенями свободы; сейчас корпус закреплён.
- **Свободная поверхность не считалась.** Шаблон `openfoam-vof` написан и
  разворачивается, но настоящим запуском не проверен: одна такая постановка —
  это сутки на этой машине.
- **Волны.** Семейство `waves` объявлено в схеме, случаев нет: §5.6 запускается
  только если натурные данные покажут, что нынешняя модель недостаточна.
- **Чувствительность к постановке (§4.4).** Одна модель турбулентности, одни
  пристеночные функции. Проверен пока только размер домена, и только у киля.

## Батарея

```sh
make t-cfd
```

Полсекунды, входит в `make test`. Проверяет оси, схему манифеста, геометрию,
разбор истории сил, оценку сходимости на изготовленном решении с известным
порядком, разворачивание всех шаблонов всеми случаями, правило статуса и
сквозной путь «сводка → сходимость → отчёт» на поддельном выводе решателя.

Живой мост к симулятору проверяется, если есть `node` и собран
`out/export/physics.json`; иначе эта часть пропускается с явной строкой, а не
молча.
