# Поддержание документации

## Где хранится утверждение

| Сведения | Основное место |
|---|---|
| Пользовательские цели и критерий обучения | `docs/project/goals.md` |
| Текущий режим, ограничения и открытые блокеры | `docs/project/status.md` |
| Ответственность, входы, выходы и устройство кода | `docs/subsystems/` |
| Оси, единицы и контракты | `docs/reference/` |
| Обязательные правила агентов | `AGENTS.md` |
| Выполняемые команды и рабочие процедуры | `docs/guides/` |
| Длительные направления | `docs/roadmap/directions.md` |
| Ближайший эксперимент и критерий перехода | `docs/roadmap/next-steps.md` |
| Числа, источники и причины принятия/отказа | `docs/research/` |

Другие страницы ссылаются на основное место. README — вход и быстрый запуск,
CLAUDE.md — вход в AGENTS.md. README внутри каталога описывает его содержимое,
а не хранит второй список открытых задач.

## Обновление вместе с кодом

1. Найдите изменённый контракт, режим или пользовательский результат.
2. Обновите описание подсистемы; ссылки на код должны вести к существующим файлам.
3. При изменении готовности обновите статус, дату его проверки и ID задачи.
4. Запишите доказательство: ревизия, условия, команда, величина, порог, результат,
   ограничения. Отрицательные результаты не удаляются ради нового успеха.
5. Измените ближайший шаг: назовите следующий опыт и условие его завершения.
   Завершённые пункты удалите из очереди; итог остаётся в статусе/исследовании.
6. Выполните `make docs-check` и `git diff --check`; вручную сверьте команды,
   факты, пороги и отсутствие противоречий с текущим кодом.
7. Коммитьте документацию с реализацией. Если проверки не запускались, не
   переносите старое «прошло» как результат новой ревизии.

## Запись исследования

Используйте тематический раздел вместо дневника переписки. Одна запись содержит:

- вопрос и модель/геометрию, к которой относится;
- команду и условия воспроизведения, режим и исходную ревизию;
- числа и заранее назначенные критерии;
- вывод: принято, отрицательный вариант, подготовка или ещё не проверено;
- границу переноса результата и ссылку на следующую задачу.

Среднее без окна и единиц, FPS без устройства, CFD без сетки/шага/чистоты,
форма без режима ткани не являются достаточной записью. Ошибочную старую
интерпретацию замените объяснённым исправлением; полезные исходные числа и
ревизию сохраняйте. Не добавляйте новые планы внутрь результатов эксперимента.

## Устаревшие сведения

Удаляйте временные пути `/tmp`, привязки к незавершённой сессии, предложения
«сделать» уже реализованное, дубли команд, неподтверждённые открытые статусы
из старых ревью и последовательные версии одного плана. Исследовательские
причины отказа сворачивайте в таблицу с условиями и воспроизведением.
Полные старые записи восстанавливаются из Git; не копируйте весь дневник в архив.

Если старый путь используется внешним заданием, оставьте короткий указатель
на канонические страницы. Не добавляйте в указатель новые результаты и очередь.
Удаление указателя требует проверки внешнего потребителя.

## Периодическая сверка

`make docs-check` запускает `scripts/check_docs.py` без сборки и сети. Проверяются
локальные Markdown-ссылки, разделы, достижимость страниц от корневого README
и пути к документации в комментариях/выводе собственных инструментов.
Проверка охватывает отслеживаемые и новые неигнорируемые файлы. Внешние сайты,
команды в примерах и физический смысл утверждений автоматически не проверяются.
Исторические цитаты в неизменяемых JSON-манифестах описаны в
[индексе происхождения](../research/history.md).

Сверяйте документацию при завершении каждого этапа, изменении состава проверок,
сборки, формата записи, основного режима или исследовательского приоритета.
Проверяйте соответствие Makefile и CLI, датировку измерений, связи ID блокеров,
источники параметров и отсутствие недостижимых страниц.
Автоматическое поддержание по расписанию создаётся только по запросу пользователя.
